# Personal Hub — личный дашборд, брифинг и «второй мозг» (дизайн)

- **Дата:** 2026-10-26 · **Статус:** черновик; главные вопросы §19 закрыты 26.10; дополнено требованиями владельца 26.10 вечером (§20 — при расхождении с более ранними разделами прав §20); ждёт утверждения
- **Владелец:** заказчик продукта, не программист: решения по продукту его, по технике отданы строителю (ИИ-агенту)
- **Как читать:** «решено владельцем» значит его слова в грилле 26.10.2026; «выбор строителя» значит решение строителя по умолчанию, владелец может его оспорить. Всё, что строитель решил сам, собрано в §18

> Публичная копия: личные данные, адреса серверов и названия соседних проектов заменены нейтральными формулировками и плейсхолдерами (`<VPN_SUBNET>`, `desk.example.com`). Инженерные решения и их обоснования сохранены.

## 1. Зачем

У владельца много контуров (работа, личные проекты, быт), а задачи, сроки и почта разбросаны: что-то в голове, что-то в заметочном приложении, что-то в сессиях Claude Code, а договоры и страховки лежат pdf-файлами в облачном хранилище без единого списка сроков. Продление и дедлайны замечаются, когда уже горят.

Нужны три вещи, связанные одной базой:
1. **Утренний брифинг** в 9:00 (и по запросу): что сегодня в календаре, какие задачи горят, что важного пришло в почту, что истекает или требует продления.
2. **Разбор почты**: сортировка, удаление ненужного, отписки, сохранение интересного. Сначала система только предлагает, правила появляются из решений владельца (решено владельцем).
3. **«Второй мозг» бытовой рутины**: договоры, аренда, страховки, заметки, pdf. У него можно спросить: «когда заканчивается страховка автомобиля», «что продлевать в декабре», «найди договор аренды».

## 2. Цели, не-цели, анти-цели

**Цели:**
- каждый день в 9:00 по местному времени в Telegram приходит брифинг, который читается за 2 минуты с телефона;
- ни один срок из реестра не пропускается: предупреждения приходят за 30 дней и за 7 дней до даты «продлить до» (выбор строителя, пороги настраиваются);
- вопрос о бытовых документах в Telegram получает ответ со ссылкой на файл в облаке;
- через 2–3 недели почта разбирается по утверждённым правилам, а владелец видит только новое и важное;
- веб-дашборд показывает всё это на одном экране (решено владельцем: Telegram + дашборд).

**Не-цели (пока):**
- ответы на письма от имени владельца;
- запись в календарь (только чтение);
- рабочая почта на Exchange: владелец её не выбрал;
- мобильное приложение;
- ~~совместная работа: система для одного человека~~ — отменено 26.10: несколько пользователей, §20.1.

**Анти-цели:**
- **ничего необратимого без правила или нажатия.** Безвозвратного удаления нет совсем: только корзина. Отписка только по стандартному заголовку письма (§7.4);
- **сроки не хранятся в двух местах.** Даты живут только в базе (§3);
- **личные документы не уходят посторонним.** LLM только Anthropic (§13), файлы не копируются с облака на постоянное хранение (§6.2);
- **система не становится тяжёлой в обслуживании.** Один контейнер, SQLite, никаких очередей и брокеров (§5).

## 3. Главные принципы

1. **Сначала предлагаю, потом правила, потом работаю по правилам** (решено владельцем, относится к почте и вообще к любым действиям с внешними сервисами).
2. **Три слоя «второго мозга»** (решено владельцем: «файлы в облаке, инфа в БД, что-то в заметочном приложении»):
   - облачное хранилище (WebDAV) хранит оригиналы. Это источник правды для файлов;
   - база на VPS хранит структурированные факты: что за документ, с кем, даты, суммы, где файл. Это **единственный** источник правды для дат;
   - Заметочное приложение (локальный волт) хранит свободные заметки владельца. VPS в волт не пишет (решено владельцем 26.10, §19).
3. **Всё, что извлекла модель, сначала подтверждается.** Новая карточка документа попадает в реестр только после «✅» владельца в Telegram. Ошибка в дате дороже всего: пропустишь продление.

## 5. Архитектура

### 5.1. Почему один сервис

Памяти на сервере мало, а пользователей единицы. Поэтому один Python-процесс в одном контейнере с модулями внутри, без микросервисов (выбор строителя). Расписание — внутри процесса (APScheduler), состояние — SQLite в томе.

### 5.2. Схема

```
          ┌──────────── personal-hub (1 контейнер) ─────────────┐
 Telegram ◄──► bot ──┐                                           │
                     ├──► core: registry · tasks · rules · brief │
 VPN-браузер ◄─► web ┘           │                               │
                                 ▼                               │
                          SQLite (+FTS5)                         │
                                 ▲                               │
   scheduler ─► connectors: imap(3) · gcal · caldav · webdav ────┘
                                 │
                       Anthropic API (haiku / sonnet)
```

### 5.3. Модули

| Модуль | Что делает |
|---|---|
| `connectors/mail` | IMAP для всех трёх ящиков одним кодом, пароли приложений (выбор строителя: один протокол вместо Gmail API + IMAP). Чтение заголовков и тела, перемещение в папки, корзина |
| `connectors/calendar` | Google Calendar API (OAuth, только чтение) + CalDAV для Яндекса |
| `connectors/cloud` | WebDAV облачного хранилища: список файлов, чтение, только чтение |
| `registry` | реестр объектов быта и их сроков (§6) |
| `tasks` | задачи (§9) |
| `mail_triage` | классификация писем, предложения, правила (§7) |
| `brief` | сборка брифинга (§10) |
| `ask` | ответы на вопросы: Sonnet с инструментами поиска по базе (§6.4) |
| `bot` | Telegram-бот на aiogram, только чат владельца (§11) |
| `web` | дашборд: FastAPI + серверные шаблоны (§12) |

### 5.4. Стек (выбор строителя)

Python 3.12, aiogram 3, FastAPI + Jinja2 + HTMX (без отдельного фронтенд-сборщика), SQLite + FTS5, APScheduler, `anthropic` SDK, `pypdf` для текстовых pdf. Тот же язык и те же библиотеки, что у других Python-проектов владельца, чтобы общий код можно было позже переиспользовать (см. §19, вопрос 1).

## 6. Второй мозг

### 6.1. Модель данных реестра

Таблица `items` — «объект быта»:

| Поле | Пример |
|---|---|
| `kind` | `insurance`, `rent`, `contract`, `subscription`, `document` (паспорт, права), `warranty`, `other` |
| `title` | «Страховка автомобиля» |
| `counterparty` | «Страховая компания» |
| `start_date`, `end_date` | 2026-03-15 / 2027-03-14 |
| `renew_by` | дата, к которой надо действовать (по умолчанию `end_date`; для аренды может быть раньше из-за срока уведомления) |
| `auto_renew` | да / нет / неизвестно |
| `amount`, `period` | 10 000 ₽ / год |
| `files` | пути в облаке (один объект — несколько файлов) |
| `notes` | свободный текст |
| `status` | `active`, `expired`, `renewed`, `archived` |
| `confirmed` | подтверждено владельцем (только такие идут в брифинг как факты) |

Плюс таблица `documents` (файл в облаке: путь, хеш, извлечённый текст, дата обработки) и FTS-индекс по тексту.

### 6.2. Поступление документов

1. Раз в час `connectors/cloud` смотрит отслеживаемые папки облака и находит новые или изменённые файлы (по хешу или дате).
2. Текст: у текстовых pdf через `pypdf`; у сканов и фото файл отправляется в Haiku как изображение или PDF (выбор строителя: без локального OCR, ради экономии памяти).
3. Haiku извлекает поля карточки по JSON-схеме. Если не уверен, оставляет поле пустым, а не угадывает.
4. Бот присылает карточку: «Нашёл: Страховка автомобиля, <страховая>, до 14.03.2027. ✅ / ✏️ / ❌». Правка свободным текстом («дата 15.03»).
5. После ✅ карточка попадает в реестр. Файл в постоянное хранение не копируется, на VPS остаются только извлечённый текст и метаданные.

Ручной ввод тоже есть: «/add страховка квартиры, <страховая>, до 01.06.2027» или фото документа в бот.

### 6.3. Сроки

Каждый день перед брифингом `registry` выбирает объекты, у которых `renew_by` попадает в окно 30 дней, и отдельно — в окно 7 дней. Просроченные без отметки «продлено» висят в брифинге каждый день. Кнопки: «продлил» (спрашивает новую дату или ждёт новый файл), «не продлеваю» (в архив), «напомнить через N дней».

### 6.4. Вопросы

`/ask` или просто текст боту. Sonnet получает инструменты `search_items` (фильтры по типу, датам, контрагенту), `search_text` (FTS по документам), `get_item`, `list_expiring`. Ответ всегда со ссылкой на объект и путём к файлу в облаке. Если не нашёл, так и говорит.

### 6.5. Заметочное приложение (волт)

VPS в волт не пишет и волт не читает (решено владельцем 26.10). Статус сроков смотрится в боте (`/expiring`) и на дашборде. Заметки «Быт» владелец по желанию ведёт в волте сам. Вернуться к связке с волтом — после фазы 1, если понадобится.

## 7. Почта

### 7.1. Ящики и доступ

Три ящика через IMAP с паролями приложений (§5.3). Обрабатываются только новые письма с момента подключения, плюс разовый прогон по последним 30 дням для этапа наблюдения (выбор строителя).

### 7.2. Классы писем

Haiku раскладывает каждое письмо по одному классу (выбор строителя, список правится в §18):
`важное-лично` · `важное-работа` · `счёт/оплата` · `документ/договор` (кандидат в реестр, §6) · `рассылка-интересная` · `рассылка-ненужная` · `уведомление-сервиса` · `реклама` · `спам-подобное`.

Для каждого письма модель видит только отправителя, тему, первые ~2000 символов текста и заголовок `List-Unsubscribe`. Вложения не отправляются, кроме писем класса «документ/договор», и только после подтверждения.

### 7.3. Три этапа (решено владельцем)

1. **Наблюдение, 1–2 недели.** Ничего не трогаем. В брифинге раздел «Почта»: важное поштучно, остальное сводкой по отправителям с предложениями: «12 писем от X → отписаться?», «30 уведомлений → в архив?», «статья Y → сохранить в мозг?». Кнопки «да / нет / всегда так».
2. **Правила.** «Всегда так» создаёт правило вида `условие (отправитель / домен / тема / класс) → действие`. Правила видны и правятся в боте (`/rules`) и на дашборде. Без явного «всегда так» правило не появляется.
3. **Работа по правилам.** Письма, подходящие под утверждённое правило, обрабатываются сами, в брифинге остаётся строка «по правилам: 40 в архив, 3 отписки». Письма, не подходящие ни под одно правило, снова идут через «предложить».

### 7.4. Действия и предохранители

| Действие | Как | Предохранитель |
|---|---|---|
| В архив / в папку | IMAP MOVE | — |
| Удалить | только в корзину ящика | лимит 200 писем в сутки на ящик (выбор строителя) |
| Отписаться | только по заголовку `List-Unsubscribe`: one-click POST (RFC 8058) или письмо на `mailto:`. По ссылкам из тела письма бот **никогда** не ходит | нет заголовка — бот говорит «отпишись сам» и даёт ссылку владельцу |
| Сохранить в мозг | текст или ссылка уходят в базу как заметка с тегом; ищутся через `/ask` и видны на дашборде | — |
| Ответить / переслать | не делаем (§2) | — |

Каждое действие пишется в журнал (письмо, правило, время) и откатывается из дашборда, пока письмо в корзине.

## 8. Календарь

Только чтение: события на сегодня и завтра, пересечения, «окна» больше часа. В брифинг идут события из всех подключённых календарей одним списком.

## 9. Задачи

- **Хранение:** таблица `tasks` в базе: текст, контур (фиксированный список вроде `личное`, `работа`, `хобби`, `учёба`, `финансы`, `быт` — выбор строителя, правится в коде), срок, приоритет, статус, источник.
- **Ввод:** боту текстом («задача: позвонить в УК до пятницы»), Haiku разбирает срок и контур; кнопкой «в задачи» из письма; из реестра (сроки продления становятся задачами автоматически).
- **Разовый сбор (решено владельцем: «что-то нужно собрать из сессий»):** локальный скрипт на ПК проходит по транскриптам Claude Code (`~/.claude/projects/**`) и по `- [ ]` в волте, Haiku вытаскивает невыполненные обещания и задачи, владелец просматривает список в боте или файле и отмечает, что импортировать. Транскрипты на VPS не уезжают.
- **Задачи из волта на постоянной основе** не синхронизируются: волт с VPS не связан. Источник правды для задач — база.

## 10. Брифинг

- **Когда:** 9:00 Europe/Moscow каждый день и по `/brief` (решено владельцем).
- **Порядок (выбор строителя):**
  1. Сегодня в календаре.
  2. Горит: просроченные задачи и задачи на сегодня.
  3. Сроки: просроченное, ≤ 7 дней, ≤ 30 дней (§6.3).
  4. Почта: важное поштучно (одна строка на письмо), затем сводка и предложения (§7.3).
  5. Карточки на подтверждение, если накопились.
- **Объём:** одно сообщение Telegram (≤ 4096 символов), остальное по кнопке «подробнее» или на дашборде.
- **Кто пишет:** данные собирает код, Sonnet только формулирует. Даты и цифры подставляются из базы, а не пересказываются моделью, чтобы она не перепутала дату.
- **Если Anthropic недоступен:** повтор через 15 минут, до 4 раз; затем уходит «сырой» брифинг без формулировок модели, собранный кодом.

## 11. Telegram-бот

- **Новый личный бот** (выбор строителя: отдельный от рабочих ботов владельца, чтобы личное не пересекалось с работой). Отвечает только на `chat_id` владельца, остальным молчит.
- Команды: `/brief`, `/ask`, `/add`, `/tasks`, `/expiring`, `/rules`, `/mail`. Свободный текст: вопрос или задача (Haiku решает, что это).
- Кнопки под предложениями и карточками (§6.2, §7.3).
- Вебхук через nginx-контейнер или long polling (выбор строителя: **long polling**, чтобы не открывать новый публичный домен).

## 12. Дашборд

- Доступ только через VPN по allowlist nginx (§4). Отдельного логина нет (решено владельцем: доступ = VPN).
- **Домен `desk.example.com`** (решено владельцем 26.10: поддомен существующего домена; имя — выбор строителя). A-запись на VPS, TLS через тот же общий reverse proxy, что у соседей, доступ по allowlist VPN. Имя попадёт в публичные логи сертификатов, поэтому оно нейтральное.
- Экран: брифинг дня сверху; дальше колонки «Задачи», «Сроки», «Почта» (предложения, правила, журнал действий с откатом), «Календарь».
- Можно: отметить задачу, подтвердить или поправить карточку, редактировать правила, откатить действие с письмом.
- Фаза 3 (§15): до неё всё делается из бота.

## 13. LLM и деньги

| Задача | Модель |
|---|---|
| Классификация писем, разбор задач, извлечение полей карточки | `claude-haiku-5-5` |
| Брифинг, вопросы `/ask` | `claude-sonnet-5-5` |

- Провайдер один: Anthropic API напрямую (решено владельцем). API не использует запросы для обучения по умолчанию. Исключение — только аудио голосовых, оно уходит в Gemini (§20.3).
- Ключ на старте — общий с другим проектом (решено владельцем, техдолг §16). Каждый запрос получает метку `personal-hub` в `metadata`, чтобы расходы отделялись.
- **Свой предохранитель:** дневной лимит токенов в коде (выбор строителя: 2M входящих / 200k исходящих в сутки). При превышении — только сырой брифинг и уведомление владельцу. Защищает и от ошибки в цикле, и общий ключ.
- Что уходит в модель: заголовки и начало писем, тексты документов при извлечении, данные базы при брифинге и вопросах. Пароли и реквизиты не уходят: перед отправкой номера карт и паспортов маскируются регуляркой (выбор строителя).

## 14. Безопасность и эксплуатация

- **Секреты:** `/opt/personal-hub/.env` (права 600): ключ Anthropic, токен бота, `chat_id`, пароли приложений трёх ящиков, OAuth-токен Google, пароль WebDAV. В репозитории только `.env.example`.
- **Доступ к ящикам** даёт полную власть над почтой, поэтому пароли приложений, а не основные пароли, и их можно отозвать в любой момент.
- **Бэкап:** ежедневный дамп SQLite, шифрование `age`, загрузка в облачное хранилище в отдельную папку; хранить 30 дней (выбор строителя). Проверка восстановления — раз в месяц, автоматически.
- **Мониторинг:** если брифинг не ушёл к 9:15, бот шлёт «брифинг сломался: <причина>». Ошибки коннекторов (протух пароль, OAuth) приходят владельцу отдельным сообщением раз в сутки, без спама.
- **Деплой:** Docker Compose, один сервис; лимит памяти контейнера 300 МБ.

Владелец добавил три требования: несколько пользователей (второй пользователь — партнёр владельца), подключение разных почт и ввод текстом или голосом, где часть записей — не задачи, а заметки, мысли «на осмысление» или крупные задачи под декомпозицию. На уточняющие вопросы владелец пока не ответил, поэтому ниже **выбор строителя по умолчанию**; пункты, которые владелец должен подтвердить, помечены ❓ и собраны в §20.5.

### 20.1. Несколько пользователей

- **Правило доступа (решено владельцем 26.10):** пользователь не видит чужих данных, **если они не расшарены**. Всё новое по умолчанию личное.
- **Как расшаривать (выбор строителя):** у каждой записи (задача, объект реестра, заметка, раздел) есть владелец и список доступа: «только я», конкретные пользователи или пространство. Пространство «Семья» — общее для его участников; всё, что создано в семейном чате (§20.7), сразу попадает туда. Личную запись можно расшарить кнопкой «поделиться» в боте. Сроки общих объектов приходят в брифинг всем, у кого есть доступ.
- Все таблицы получают `owner_id`, а доступ проверяется по списку доступа в одном месте кода (слой доступа), не в каждом обработчике. Тест: пользователь Б не видит ни одной нерасшаренной записи пользователя А ни через бот, ни через дашборд, ни через `/ask`; после «поделиться» видит ровно эту запись.
- Почта и подключённые ящики не расшариваются никогда (выбор строителя): расшарить можно только сохранённое из письма.
- **Вход в бот:** владелец (роль `admin`) создаёт приглашение `/invite`, бот даёт одноразовую ссылку `t.me/<бот>?start=<код>` на 24 часа. Кто по ней пришёл, становится пользователем. Остальным бот молчит.
- **Дашборд (решено владельцем 26.10: «так же, как у меня»):** у всех пользователей одинаково — `desk.example.com` открывается только из VPN, наружу не публикуется. Партнёру нужен доступ к VPN: дома — через домашний роутер, если его трафик к VPS идёт через WireGuard (его подсеть в allowlist), вне дома — свой пир WireGuard на телефоне (выбор строителя: проверить при подключении).
- **Кто зашёл (выбор строителя):** VPN сам по себе не говорит, кто за браузером: из дома оба приходят с одного адреса роутера. Поэтому вход по одноразовой ссылке из бота: `/web` → ссылка на 10 минут → cookie на 30 дней. Пароля нет, второй системы входа нет. Это меняет §12 «отдельного логина нет»: вход есть, но он через бота и только внутри VPN.
- **Честно перед пользователями:** администратор сервера технически может прочитать любые данные на нём. Это надо сказать каждому пользователю до подключения (выбор строителя: фраза в приветствии бота).
- **Деньги:** расход LLM считается по `user_id`; дневной лимит из §13 действует на каждого пользователя отдельно.
- **Брифинг:** у каждого свой, время настраивается (`/settings`), по умолчанию 9:00.

### 20.2. Подключение почт, календарей и облака

- **Мастер подключения** — в боте кнопка «Подключить почту» открывает мини-приложение Telegram (Web App) с формой: выбрать провайдера → инструкция, где взять пароль приложения, со ссылкой → поле пароля → «проверить соединение» → готово. Пароли **не пишутся в чат бота**, чтобы не остаться в истории переписки (выбор строителя).
- **Провайдеры:** Gmail, Яндекс, Mail.ru — готовые настройки IMAP; «другой» — ручной ввод сервера и порта. Gmail дополнительно через OAuth, если пароль приложения недоступен (выбор строителя: OAuth — во вторую очередь, он требует проверки приложения у Google).
- Календари: Google — OAuth в том же мастере; Яндекс и любой CalDAV — пароль приложения. Облако — пароль приложения WebDAV.
- **Хранение:** учётные данные каждого пользователя шифруются в базе (ключ шифрования только в `.env`, §14). Отключить ящик можно в один клик, данные удаляются сразу.
- Ящиков у пользователя может быть сколько угодно; правила почты (§7) — свои у каждого пользователя.

### 20.3. Ввод текстом и голосом

- **Каналы:** общение с человеком — только Telegram-бот (решено владельцем 26.10): текст, голосовое, фото, pdf, пересланные сообщения. Поле быстрого ввода и загрузка файлов на дашборде — фаза 3. Плюс MCP-сервер для Claude (§20.11).
- **Голос — только бесплатно (решено владельцем 26.10).** Платные сервисы отпали: Yandex SpeechKit не имеет постоянного бесплатного лимита (~0,8 ₽/мин асинхронно), SaluteSpeech с 15.07.2026 не продаёт пакеты физлицам, `@smartspeech_sber_bot` недоступен (боты пишут друг другу, только если оба включили этот режим), а Telegram отдаёт свою расшифровку только людям в приложении, не ботам (проверено по документации 26.10).
  - Claude аудио не принимает (Haiku/Sonnet 5.5 — текст, изображения, pdf; проверено по документации Anthropic 26.10).
  - **Решено владельцем 26.10 («давай попробуем»): голосовые расшифровывает Google Gemini через AI Studio на бесплатном уровне.** Голосовое (OGG Opus) уходит в актуальную Flash-модель с бесплатным уровнем (какую именно — проверить при установке) с одной задачей: дословная расшифровка, без пересказа. Бот показывает текст, дальше запись разбирает Claude по §20.4. Памяти на сервере не занимает.
  - **Ключ на старте — общий ключ AI Studio другого проекта** (техдолг §16, как с ключом Anthropic).
  - **Приватность:** на бесплатном уровне Google может использовать присланное для улучшения своих продуктов. Поэтому в Gemini уходит **только аудио голосовых**, ничего больше: документы, почта, база и расшифрованный текст — только в Claude. Бот предупреждает об этом в приветствии: «не диктуйте голосом номера документов, здоровье, деньги — напишите текстом».
  - **Если бесплатный лимит кончился или Gemini недоступен:** бот отвечает подсказкой расшифровать голосовое в Telegram («→A») или надиктовать клавиатурой и прислать текстом. Этот же путь работает всегда, без Gemini.
  - Критерий: на 10 настоящих голосовых владельца расшифровка ошибается не больше чем в одном слове из десяти. Иначе остаётся только текстовый путь.
- **Файлы из бота** сохраняются в облако пользователя в папку `Входящие` и дальше идут по §6.2. Для этого доступ к облаку становится «чтение + запись в одну папку» (меняет §5.3 «только чтение»).

### 20.4. Что это: задача, заметка, мысль или проект

Haiku раскладывает каждую запись по типу, бот показывает тип кнопкой и даёт сменить одним нажатием:

| Тип | Что значит | Что происходит |
|---|---|---|
| `задача` | понятно, что сделать | в задачи, срок и контур — из текста (§9) |
| `проект` | крупная задача из нескольких шагов («переоформить машину», «подготовить праздник») | Sonnet предлагает разбивку на 3–7 подзадач, пользователь правит и подтверждает; подзадачи ссылаются на проект |
| `подумать` | мысль, которую надо осмыслить, решения ещё нет | в список «Подумать». Раз в неделю (выбор строителя) брифинг поднимает одну-две мысли; команда `/think` открывает разговор с Sonnet по выбранной мысли, итог сохраняется в заметку, а из неё можно сделать задачи |
| `заметка` | просто запомнить | в базу как заметка, ищется через `/ask` |
| `документ` | файл или фото документа | §6.2 |
| `вопрос` | вопрос к мозгу | §6.4 |

### 20.7. Семейный чат

Владелец предложил привязать существующую семейную группу в Telegram (далее «Семейный чат»; решено владельцем 26.10, детали ❓ в §20.10).

- Бот добавляется в группу. Группа = пространство «Семья», участники группы, прошедшие приглашение, — его участники.
- **Что бот берёт из чата (выбор строителя ❓):** только то, что адресовано ему: упоминание `@бот`, ответ на сообщение бота, команда или реакция 📌 на любое сообщение («забери это»). Остальную переписку бот не читает и не хранит. Для этого у бота остаётся включён privacy mode Telegram, а реакции он получает как админ группы.
- Записи из чата разбираются по типам §20.4 и сразу общие. Ответ бота в группе короткий: «📌 Задача: купить билеты до 10.11 → раздел Отпуск».
- В группу приходит общий «семейный» брифинг: только расшаренное (общие сроки, общие задачи на день). Личные брифинги остаются в личке с ботом (выбор строителя).

### 20.8. Разделы

Владелец: «есть всякие разделы, типо отпуск, куда мы накидываем всякое». Это новая сущность.

- **Раздел** — именованная подборка всего вперемешку: задачи, заметки, ссылки, файлы, объекты реестра, страницы Notion. Примеры: «Отпуск», «Ремонт», «Машина». У раздела есть владелец и доступ, как у любой записи (§20.1).
- **Как разделы устроены сейчас (посмотрел строитель 26.10 по просьбе владельца):** в Notion. Типичный пример — страница-хаб проекта (например, подготовка к событию): база «Задачи» (поля `Задача`, `Статус` Not started / In progress / Done, `Дедлайн`, `Приоритет`, `Категория`, `Бюджет`, `Заметки`), база «Список участников», подстраницы с планами. Значит, раздел personal-hub — это обычно **страница-хаб Notion с базой задач** (§20.9). Устройство самого семейного чата строитель увидеть не может (нет доступа к Telegram владельца); проверит, когда бот будет добавлен в группу.
- Если группа — форум с темами, тема привязывается к разделу: всё, что отправлено боту в теме «Отпуск», попадает в раздел «Отпуск». Если тем нет — работает только выбор раздела по смыслу и командой (выбор строителя: код поддерживает оба случая).
- Вне темы бот сам предлагает раздел по смыслу, а «/раздел Отпуск» меняет его вручную.
- В разделе можно спросить: «что у нас по отпуску?» — Sonnet собирает сводку раздела: открытые задачи, ключевые заметки, ссылки, сроки.
- У раздела может быть срок жизни (отпуск закончился → раздел в архив по кнопке).

### 20.9. Страницы Notion

- К разделу или записи можно привязать страницу или базу Notion ссылкой (решено владельцем: «привязка страниц из ноушен»).
- **Доступ:** внутренняя интеграция Notion на пользователя — токен через мастер подключения (§20.2); пользователь сам даёт интеграции доступ к нужным страницам. Чтение **и запись** (решено владельцем 26.10).
- **Чтение:** раз в час забираем текст привязанных страниц и строки их баз в кэш для поиска и сводок раздела.
- **Запись (выбор строителя — границы):**
  - если у раздела есть база задач Notion, она — источник правды для задач этого раздела: задача из бота создаётся строкой в этой базе, «сделано» меняет `Статус`, срок пишется в `Дедлайн`. Поля сопоставляются по типу (заголовок, статус, дата, select); значение select (`Категория`, `Приоритет`) Haiku выбирает только из существующих вариантов, новых не создаёт;
  - заметка из бота дописывается в конец страницы раздела отдельным блоком с датой и автором;
  - **никогда:** не удаляем страницы и строки, не переписываем существующий текст, не меняем схему баз;
  - конфликт: если строку правили в Notion позже нас — побеждает Notion, бот сообщает о расхождении.
- Ограничение Notion API ~3 запроса/с: запись идёт через очередь.
- **Другие пользователи и Notion (решено владельцем 26.10):** Notion только у владельца. Задачи и заметки второго пользователя в расшаренном разделе пишутся в Notion **через интеграцию владельца**. Чтобы было видно, чьё это: автор записывается в `Заметки` строки («от: <имя>») и в блок заметки (выбор строителя). Второй пользователь страниц Notion не открывает, поэтому бот показывает ему содержимое раздела из кэша, а не ссылку на Notion.
- **Только расшаренные страницы (решено владельцем 26.10):** пользователь видит и пишет только в те страницы Notion, которые владелец явно ему расшарил. Единица шаринга — отдельная страница или база Notion, а не весь раздел: в разделе «Отпуск» владелец может открыть партнёру базу задач и не открывать подстраницу с бюджетом. Новые подстраницы расшаренной страницы автоматически не открываются (выбор строителя).
- Интеграция владельца видит все его подключённые страницы, но пользователю доступно только расшаренное ему. Это проверяет тот же слой доступа (§20.1): у второго пользователя нет пути к остальным страницам Notion владельца ни через `/ask`, ни через сводки.
- Если раздел создан в боте и не привязан к Notion — живёт только в нашей базе; привязать можно позже командой.

### 20.11. MCP-сервер для Claude

**Решено владельцем 26.10:** «нужна сама возможность подключить MCP; какие приложения — пока не ясно, решим позже».

- **Что это:** модуль `mcp` внутри того же процесса, удалённый MCP-сервер по Streamable HTTP. Через него Claude (Code, Desktop, мобильное приложение или claude.ai — по будущему решению) добавляет задачи и заметки, спрашивает мозг, смотрит сроки и разделы.
- **Инструменты (выбор строителя):** `add_entry` (текст → разбор по §20.4, как в боте), `list_tasks`, `complete_task`, `search` (реестр, заметки, разделы, Notion-кэш), `list_expiring`, `get_section`, `get_brief`. Удалять ничего нельзя, почту трогать нельзя: MCP-сервер не получает инструментов для действий с письмами (выбор строителя).
- **Кто подключился:** каждый пользователь получает свой токен в боте командой `/mcp` (можно отозвать там же). Доступ проверяет тот же слой доступа (§20.1): через MCP пользователь видит ровно то же, что в боте.
- **Сеть — зависит от будущего решения:**
  - Claude Code и Desktop на ПК подключаются изнутри VPN, как дашборд: ничего открывать не нужно. **С этого и начинаем** (выбор строителя);
  - коннекторы мобильного Claude и claude.ai ходят к серверу из облака Anthropic, а не с устройства пользователя. Для них придётся открыть в интернет один путь (`desk.example.com/mcp`) со входом по OAuth. Это отступление от «наружу не публиковать», поэтому только по отдельному слову владельца. Код входа строится так, чтобы OAuth добавлялся без переделки инструментов.
- Фаза 5. Критерий: из Claude Code на ПК владельца через VPN добавлена задача, найден документ реестра и получен брифинг; токен второго пользователя не видит нерасшаренного.

## 21. Дашборд: решения 27.10.2026

Источник — исследование `docs/research/2026-10-26-dashboard-research.md` (§0 и «Решение владельца») и ответы владельца 27.10. При расхождении с §12 и §20 прав §21.

1. **Порядок (решено владельцем):** план 1c (веб-дашборд, вход, настройки, календари) идёт раньше 1b (документы). Облако в 1b подключается уже через страницу «Настройки».
2. **Стиль (решено владельцем):** вариант A «Строгий» — токены в исследовании; макеты экранов «Сегодня», «Задачи», «Почта», «Документы», «Настройки» делались интерактивной страницей (в репозиторий не входят). Тёмная тема — по системной настройке и по теме Telegram.
3. **Стек вёрстки (выбор строителя по исследованию):** FastAPI + Jinja2 + HTMX, daisyUI 5 поверх Tailwind 4; CSS собирается standalone-бинарником Tailwind на этапе сборки Docker-образа (без Node на сервере), отдаётся как статический файл с того же домена. Цвета — свои CSS-переменные с цепочкой `var(--tg-theme-…, <цвет A>)`.
4. **Один процесс:** веб-сервер (uvicorn) работает в том же процессе и event loop, что бот и планировщик; одна база.
5. **Вход:** (а) в браузере — `/web` в боте даёт одноразовую ссылку на 10 минут → cookie сессии на 30 дней (`HttpOnly; Secure; SameSite=Lax`); (б) в мини-приложении Telegram — `initData`, проверка HMAC-SHA256 с ключом `WebAppData`, `auth_date` не старше 60 минут, пользователь зарегистрирован → та же сессия. Токен сессии передаётся и cookie, и заголовком `Authorization` (HTMX `htmx:configRequest`), потому что в Telegram Desktop/Web cookie может не доходить. 401 → заголовок `HX-Trigger: reauth`.
6. **Один origin:** всё на `desk.example.com`, никаких поддоменов (Bot API 10.2 блокирует методы мини-приложения с чужого origin). CSP `frame-ancestors 'self' https://web.telegram.org`.
7. **Календари (решено владельцем):** подключаются **секретной ссылкой iCal** (Google: «Секретный адрес в формате iCal»; Яндекс: ссылка экспорта) — только чтение, без OAuth. Ссылка — секрет, хранится зашифрованной (§20.2). Опрос раз в 15 минут; задержка обновлений у самих Google/Яндекса — до нескольких часов, это принимается. Это заменяет OAuth из §20.2 для календарей.
8. **Подключения:** общая таблица подключений со статусами `ok | error | auth_expired | disabled`, «синхронизировано N мин назад», кнопки «Проверить» и «Переподключить» (модель из исследования). Секреты шифруются ключом из `.env` (Fernet). В 1c — вид `ics_calendar`; облако WebDAV и почта добавят свои виды в 1b и фазе 2.
9. **Экраны 1c:** «Сегодня» (брифинг + календарь на сегодня), «Задачи» (как в боте: ввод, группы, разделы, «выполнено / отменить / вернуть», поделиться), «Настройки» (подключения, время брифинга, расход модели, доступы, пользователи для админа). Вкладки «Почта» и «Документы» есть в навигации, но показывают «появится позже».
10. **Телефон и ПК:** на телефоне нижняя панель из 4 вкладок, настройки — иконкой в шапке; от 1024 px — боковое меню и 2 колонки на «Сегодня».
